Problem Statement2.1  The Incident Response Crisis in IndiaIndia has over 63 million Small and Medium Businesses (SMBs), plus thousands of colleges, hospitals, and NGOs. Almost none of them have a dedicated cybersecurity team or an incident response plan. When a cyberattack happens — ransomware, phishing, data breach — the response is ad-hoc, chaotic, and legally non-compliant.The consequences are severe. Organizations lose data, face reputational damage, and increasingly face legal exposure under India's Digital Personal Data Protection (DPDP) Act 2023, which mandates breach reporting within 6 hours to CERT-In and within 72 hours to the Data Protection Board.Core Problem DimensionsNo Security Team: Colleges, hospitals, NGOs, and startups have zero dedicated security staff or IR budget. When a breach happens, the IT team (or worse, a student volunteer) is expected to handle it.No Incident Plan: Response is ad-hoc, typically via WhatsApp groups. No documentation. No process. No chain of command. Every second of uncoordinated response lets the attacker go deeper.No Legal Compliance: The DPDP Act 2023 Section 8(6) requires breach notification within 6 hours of detection. Most organizations are unaware of this obligation and completely unprepared to meet it.No Visibility: After an incident, organizations cannot answer: What was compromised? When? How much data? Who was affected? Without this, they cannot prevent recurrence.2.2  Target AudienceOrganizationTheir ProblemWhat ZeroRespond ProvidesCollege IT DeptsAd-hoc response. System Architecture5.1  Architecture OverviewZeroRespond is built as a multi-layer platform. Log sources feed into the Wazuh detection engine, which processes and normalizes events, correlates against detection rules, and generates alerts. These alerts are consumed by the ZeroRespond application layer — comprising the Case Manager, Playbook Engine, and Report Generator — all backed by a PostgreSQL database. The ZeroDashboard frontend consumes data from the backend REST API and displays it in real time.   All components run as Docker containers on a single Linux server. The entire stack can be deployed with 'docker compose up' in one command.Data FlowLog sources (Windows events, Linux syslogs, firewalls, web servers) ship logs to the Wazuh agent or directly to the Wazuh manager.Wazuh ingests, normalizes, and runs correlation rules. Anomalies trigger alerts stored in the OpenSearch indexer.The ZeroRespond Alert Processor polls Wazuh via API. Critical and high-severity alerts trigger automatic case creation in the Case Manager.When a case is created, the Playbook Engine identifies the attack type and attaches the appropriate response playbook to the case.The responder follows playbook steps through the ZeroDashboard UI. Each completed step is timestamped and stored in PostgreSQL.When the case is marked resolved, the Report Generator pulls all case data and generates a DPDP-compliant PDF report.The ZeroDashboard aggregates all cases and presents MTTD, MTTR, severity trends, and incident heatmaps in real time.5.2  Technology StackDetection EngineWazuh 4.7 — open-source SIEM/XDR. Handles log ingestion, normalization, correlation rule evaluation, anomaly detection. Uses OpenSearch for indexing.Backend APIFastAPI (Python 3.11) — high-performance REST API. Handles case management CRUD, playbook engine logic, alert processing, report trigger endpoints.DatabasePostgreSQL 15 + SQLAlchemy ORM — stores incident cases, playbook steps, evidence records, user actions, completion timestamps.Frontend DashboardReact 18 + Tailwind CSS — ZeroDashboard UI. Real-time incident list, case detail view, playbook step-through interface, MTTD/MTTR charts.Report GeneratorWeasyPrint (primary) / Puppeteer (fallback) — converts HTML templates with case data into DPDP-compliant PDF reports.DeploymentDocker + Docker Compose — all services containerized. Single 'docker compose up' command deploys the entire stack on any Linux server.CommunicationREST APIs between all services. WebSocket connections for real-time alert push to the ZeroDashboard frontend.6. When a case is created, the engine identifies the attack type and attaches the appropriate playbook — a step-by-step, command-level response guide. This is not generic advice like 'isolate the system'. This is specific: 'Run sudo iptables -I INPUT -j DROP on the affected host to stop lateral spread'.Every step in a playbook is stored as a database record with fields: step number, title, instructions, platform-specific commands (Linux/Windows), expected outcome, and whether it is blocking (must complete before next step) or parallel (can run concurrently).The 5 Playbooks Ragul Must BuildPlaybookTrigger ConditionKey Steps (high level)Ransomware ResponseMass file rename + C2 traffic detectedIsolate host (firewall rules) → Identify malicious process (netstat/ps) → Preserve evidence (memory dump) → Kill process → Block C2 IP → Restore from backup → Generate reportPhishing / BEC ResponseSuspicious email link clicked, C2 beacon detectedIdentify affected mailbox → Reset credentials → Block sender domain → Scan for payload → Check for lateral phishing → Notify users → ReportUnauthorized AccessUnexpected admin login, off-hours accessLock account immediately → Review session logs → Check for persistence (cron, startup entries) → Audit access trail → Force re-auth all active sessions → ReportData ExfiltrationLarge outbound transfer to unknown IPBlock outbound connection → Identify exfiltrated files → Determine scope of breach → Preserve network logs → Notify DPO → Generate DPDP reportInsider ThreatUnusual bulk download, USB insertion, off-hours accessPreserve log evidence → Disable account (do not delete) → Interview manager → Escalate to HR/Legal → Document all actions → ReportPlaybook Snippet — Ransomware Step 1 (Example of Expected Quality)   Step 1: Isolate the Host Immediately

Appendix — Technical Reference12.1  ISO 27035 Incident Response PhasesZeroRespond implements the ISO 27035 IR standard across its five modules:Phase 1: PreparationCovered by Module 1 (Wazuh rules, alert thresholds configured) and Module 4 (org profile, report templates ready before an incident).Phase 2: IdentificationModule 1 (Wazuh detection) and Module 2 (case creation, initial triage in Case Manager).Phase 3: ContainmentModule 3 (Playbook Engine — containment steps are the first actions in every playbook).Phase 4: EradicationModule 3 (Playbook steps for removing the threat: killing processes, blocking IPs, removing persistence).Phase 5: RecoveryModule 2 (case resolution, recovery step completion) and Module 3 (recovery section of each playbook).Phase 6: Lessons LearnedModule 4 (incident report with recommendations) and Module 5 (MTTR/MTTD metrics to track improvement over time).12.2  Glossary of Key TermsSIEMSecurity Information and Event Management. A platform that collects, normalizes, and analyzes security logs from multiple sources.XDRExtended Detection and Response. An evolution of SIEM that also provides response capabilities across endpoints, networks, and cloud.MTTDMean Time to Detect. Average time from when a threat occurs to when the first alert is generated.MTTRMean Time to Respond. Average time from alert generation to incident containment and resolution.DPDP Act 2023India's Digital Personal Data Protection Act. Section 8(6) requires breach notification to CERT-In within 6 hours and to the Data Protection Board within 72 hours.CERT-InComputer Emergency Response Team India. The national nodal agency for cybersecurity incident response. Breaches must be reported to incident@cert-in.org.in.IOCIndicator of Compromise. Artifacts found on a network or system indicating unauthorized access. Examples: malicious IP, file hash, suspicious process name.PlaybookA documented, step-by-step response procedure for a specific type of security incident. ZeroRespond includes 5 playbooks.C2Command and Control. Infrastructure used by attackers to communicate with compromised systems. C2 traffic is a key indicator of active malware.False PositiveAn alert triggered by benign activity that is incorrectly identified as malicious. A high false positive rate causes alert fatigue.ISO 27035International standard for information security incident management.
